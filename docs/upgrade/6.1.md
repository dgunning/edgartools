# Upgrading to EdgarTools 6.1

6.1 is additive over [6.0](6.0.md): it adds features and keeps every 6.0 name
and signature. This page lists what can alter what your code receives, in the
same form as the 6.0 guide: what a call did in 6.0.0, what it does now, and a
filing where the difference was measured. There are two deprecations,
`filing.acceptance_datetime` and `ParserConfig(extract_images=...)`, and the rest
are corrected values. If you stored
any of these results, recompute them.

If you find a difference this page does not describe, it is a gap in the page;
see [Getting help](6.0.md#getting-help).

---

## `EntityFiling.acceptance_datetime` is deprecated

**What changed.** The value `Company(...).get_filings()` gives each filing as
`acceptance_datetime` is `acceptanceDateTime` from SEC's submissions JSON. SEC
labels it UTC but has served it hours off for whole companies at a time: Apple's
10-Q `0000320193-26-000020`, accepted 2026-07-31 06:01:02 ET (10:01:02 UTC),
read 14:01:02 UTC for at least two weeks of October 2026 (GH #1501). The value
is kept under a name that says what it is, and the exact time has its own
property.

| Before | Now |
|---|---|
| `filing.acceptance_datetime` | still works, with a `DeprecationWarning`; removed in 7.0 |
| | `filing.reported_acceptance_datetime`: the same value, no warning |
| `filing.header.acceptance_datetime` for the exact time (downloads the whole submission, up to 8.6 MB for a 10-Q) | `filing.accepted_at`: the exact time from `{accession}-index-headers.html` (3-20 KB), tz-aware `America/New_York`, on every `Filing` |
| a loop over `filing.header` | `filings.accepted_at()`: a Series of exact times indexed by accession number |

The `acceptanceDateTime` column of `filings.to_pandas()` is unchanged.

**Rewrite rule.** Replace `filing.acceptance_datetime` with
`filing.accepted_at` where the exact moment matters, for example deciding
whether a filing came before the 16:00 close, and with
`filing.reported_acceptance_datetime` where the reported value is enough.

## `ParserConfig(extract_images=...)` is deprecated

**What changed.** `ParserConfig.extract_images` was declared with a default of
`False` and documented as switching image extraction, but nothing read it:
every `<img>` became an `ImageNode` whatever the value. It is now accepted,
ignored as before, and raises a `DeprecationWarning`; it is removed in 7.0.
Parsing output does not change.

| Before | Now |
|---|---|
| `ParserConfig(extract_images=False)` | still constructs, with a `DeprecationWarning`; removed in 7.0 |
| `config.extract_images` read `False` | reads `None` unless you passed a value |

**Rewrite rule.** Drop the argument. `Document.text()` already leaves images
out unless you call it with `include_images=True`.

## Added: the `is_nil` column

XBRL facts now record whether the filer marked the item `xsi:nil` (GH #1254).
`Fact.is_nil` defaults to `False`, so older constructors and serialized
payloads without the key still load. It is filer metadata only: a nil fact
still has `value == ''` and `numeric_value` of `None`, and the flag does not
mean zero or a retraction.

Two things you may notice:

- **Column shape.** `is_nil` (nullable `boolean`) is the last core column of
  `FactQuery.to_dataframe()`, after `fiscal_year`, so the `dimension` and
  `dim_<axis>` columns sit one place further right. `FactsView.to_dataframe()`
  and `XBRL.to_pandas()['facts']` gain it after `fact_id`. Code that selects
  columns by name is unaffected.
- **One extra row for a nil/empty pair.** A nil item and an empty non-nil item
  that agree on concept, context, value, decimals and unit used to collapse to
  whichever came first. They are now two rows, even in a projection that does
  not include `is_nil`; dropping the column does not restore the old row count.

Statement frames, stitched queries, EntityFacts and 424B parsing do not carry
the field.

Inline-document facts (`Document.xbrl_facts`) carry it as `XBRLFact.is_nil`
(GH #1757), read by namespace whatever prefix the filer uses (`xs:nil` as well
as `xsi:nil`), and `to_dict()` gains an `is_nil` key. A nil inline fact keeps
its content as filed and is never transformed, scaled or signed: a nil fact
with `format="ixt:fixed-zero"` and `sign="-"` used to read as `-0`, and now has
`value == ''` and `numeric_value` of `None`.

A typed dimension member marked `xsi:nil` (GH #1751) used to read as the typed
element's name, `{http://fasb.org/us-gaap/2026}QName.domain`, in
`Context.dimensions`, the `dim_<axis>` columns and statement labels. Its value
is now `''`, the axis stays on the context, and the new `Context.nil_dimensions`
list names the axis (inline contexts carry a `nil_dimensions` key the same way).
Display labels show the member as `(nil)`, and `XBRL.to_pandas()['contexts']`
gains a `nil_dimensions` column.

## Errors: `Company` statement methods raise

**After 6.0.0:** `Company.income_statement()`, `balance_sheet()` and
`cash_flow_statement()` raise `ValidationError` for an invalid argument such
as `period="quarter"`, where 6.0.0 and 5.x returned `None`. An error while
building the statement, such as too little data for a TTM trend, now reaches
you too, as it already did from the same methods on `EntityFacts`. `None` now
means only that SEC has no company facts for the company (GH #1732).
`ValidationError` subclasses `ValueError`, so an existing `except ValueError:`
still catches it.
