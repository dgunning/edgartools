# Upgrading to EdgarTools 6.0

This page lists every change in 6.0 that can alter what your code receives, one
symbol at a time: what it did before, what it does now, and the rewrite where a
mechanical one exists. It is written to be enough on its own — if you are an
agent upgrading a dependent codebase, you should not need the CHANGELOG or the
commit history as well.

6.0 is still in development. This page grows as each change lands, so a change
absent here has not shipped. Items known to be coming are listed under
[Still to come](#still-to-come) so you can plan for them, but do not write code
against them yet.

!!! note "Two kinds of change"
    **Loud ones** rename, move or remove something: the cash-flow method names,
    the `edgar.effect` / `edgar.form144`, settings and date-helper moves, the
    access modes, `FilingHomepage(soup=...)`, and the legacy `edgar.files` parser
    with its page-break options. Each of these warns in 5.x
    before it breaks in 6.0, so running your code on the latest 5.x with
    warnings visible finds them.

    **Quiet ones** keep every import path and signature and change *what values
    you get back*. Your code will not fail to import, and in most cases it will
    not raise; it will return something different. A few of these warn in 5.x
    too (the error changes emit a `FutureWarning`), but most cannot, so read
    those sections closely.

## Python 3.11 or newer is required

**What changed.** EdgarTools 6.0 requires Python 3.11 or newer; 5.x supported
3.10. Python 3.10 reaches the end of its upstream security support on
2026-10-31, shortly before 6.0 ships. Nothing in the API changes with it, so on
3.11 and newer there is nothing to rewrite, and the pandas requirement is unchanged:
6.0 still works with both pandas 2.x and pandas 3.x.

**Who is affected.** Only installations running on Python 3.10. That was about
3.8% of EdgarTools downloads over the 180 days before August 2026.

**What happens on Python 3.10.** Nothing breaks in place. The 6.0 packages
declare `Requires-Python: >=3.11` in their metadata, and pip skips any release
whose `Requires-Python` excludes the running interpreter. So on 3.10:

```bash
pip install -U edgartools        # resolves to the last 5.x release, not 6.0
pip install "edgartools>=6"      # fails, naming the >=3.11 requirement
```

The first command keeps you on the newest 5.x release, which continues to work
on 3.10. The second, or installing a 6.0 wheel file directly, stops with an
error naming the Python requirement rather than installing something that
fails at import. Other resolvers that honour `Requires-Python` (uv, Poetry,
pip-tools) behave the same way. Poetry and uv check it against your project's
declared Python range rather than the interpreter you are running, so a project
that still declares 3.10 support will not get 6.0 until that range starts at
3.11, even when you run it on a newer Python.

**What to do.** Move to Python 3.11 or newer, then upgrade:

```bash
python --version                 # must report 3.11 or higher
pip install -U edgartools
```

If you cannot move off 3.10 yet, nothing is required: pip keeps resolving to
5.x on that interpreter. To make the choice explicit in a requirements file or
lockfile, pin the 5.x line:

```bash
pip install "edgartools<6"
```

## Cash flow: one name, `cash_flow_statement()`

**What changed.** Cash flow had three names depending on which object you were
holding — `Company.cash_flow()`, `Financials.cashflow_statement()` and
`xbrl.statements.cash_flow_statement()`. Only `Company` accepted all three, and
of the 16 classes offering `income_statement()`, `EntityFacts` and
`CurrentPeriodView` offered no `cash_flow_statement()` at all. It is now
`cash_flow_statement()` everywhere, matching `income_statement()` and
`balance_sheet()`.

`cashflow_statement()` and `cash_flow()` still work in 5.x and emit a
`DeprecationWarning`. **6.0 removes them.**

```python
# Before — whichever spelling that particular object happened to accept
company.cash_flow()
financials.cashflow_statement()
xbrls.statements.cash_flow_statement()

# Now — the same name on every object
company.cash_flow_statement()
financials.cash_flow_statement()
xbrls.statements.cash_flow_statement()
```

**The mechanical rewrite.** Both old spellings map to the new one with no
change in arguments or return type:

```bash
grep -rln 'cashflow_statement\|\.cash_flow(' . \
  | xargs sed -i '' -e 's/cashflow_statement/cash_flow_statement/g' \
                    -e 's/\.cash_flow(/.cash_flow_statement(/g'
```

**Why it is worth a rename.** `income_statement`, `balance_sheet`,
`cashflow_statement` — one of those three is not like the others, and the cost
landed on people least able to absorb it. Assistants suggested the wrong
spelling, autocomplete could not help across objects, and a beginner got an
`AttributeError` for a method that exists on the object next to it.

**To find your call sites now**, run with deprecation warnings visible:

```bash
python -W "default::DeprecationWarning" your_script.py
```

## `edgar.effect` and `edgar.form144` moved

**What changed.** Two single-form parsers moved to the subpackages their subject
belongs to. `Effect` now lives in `edgar.offerings.effect`, beside the S-1/S-3/S-4,
424B and Form C/D parsers — a notice of effectiveness is a registration-lifecycle
document. `Form144` now lives in `edgar.ownership.form144`, beside the Forms 3/4/5
parsers — Form 144 is an affiliate's notice of a proposed sale.

`Effect` is not exported at the top level, so its module path is its entire public
surface. `Form144` has also been exported at the top level since 5.60.0, and
`from edgar import Form144` is unaffected. From 5.55.0 the old module paths
forwarded to the new ones and emitted a `DeprecationWarning` naming the new one.
**6.0 removes them: `import edgar.effect` and `import edgar.form144` raise
`ModuleNotFoundError`.**

```python
# Before
from edgar.effect import Effect
from edgar.form144 import Form144

# Now
from edgar.offerings.effect import Effect
from edgar.ownership.form144 import Form144   # or: from edgar import Form144
```

**You may not need to do anything.** `filing.obj()` routes to the new paths, so
ordinary use never touched the old paths. This only affects code that imports the
module directly.

**Migrate on 5.x, one call site at a time.** On 5.55.0 and later the old paths
returned the same objects as the new ones, not copies, so `isinstance` checks
written against either path agree while a codebase is half migrated.

Mechanical rewrite:

```bash
sed -i '' -e 's/from edgar\.effect import/from edgar.offerings.effect import/' \
          -e 's/from edgar\.form144 import/from edgar.ownership.form144 import/' your_script.py
```

`edgar.muniadvisors` also became a package in the same release, but its import path
is unchanged and all of its public names still resolve — nothing to do.

## `period_length` on the EntityFacts statements

**What changed.** `EntityFacts.income_statement()` and
`.cash_flow_statement()` took a `period_length` argument documented as
"3=quarterly, 12=annual". It was never read — it appeared nowhere in either
method body, and had not since the Facts API landed. Asking for
`period_length=3` returned the **annual** statement, with no warning.

It is honoured now, and deprecated in the same release: `period=` is the
supported spelling and the only one that can also say `'ttm'`. **6.0 removes
`period_length`.**

```python
# Before — silently annual, whatever you passed
facts.cash_flow_statement(period_length=3)

# Now — quarterly, with a DeprecationWarning naming the replacement
facts.cash_flow_statement(period_length=3)

# The spelling to move to
facts.cash_flow_statement(period='quarterly')
```

**This one is a fix, not a break.** Nobody can have depended on the old
behaviour deliberately: there was no way to pass `period_length` and get what
the docstring promised. If a script of yours passes `period_length=3` and its
numbers change, they were wrong before — it was reading annual figures under a
quarterly label.

**Contradictions now raise.** Saying two different things at once used to be
resolved silently in favour of whichever the code happened to read:

```python
facts.income_statement(period='annual', period_length=3)   # ValidationError
facts.income_statement(period='quarterly', period_length=3)  # fine, they agree
```

`period_length` values other than 3 or 12 raise `ValidationError` as well,
rather than being ignored.

**The mechanical rewrite:**

```bash
sed -i '' -e "s/period_length=3/period='quarterly'/g" \
          -e "s/period_length=12/period='annual'/g" your_script.py
```

## `include_dimensions` is removed; use `view=`

**What changed.** Statement rendering took an `include_dimensions` boolean until
5.8.0 replaced it with `view=`, which names three presentations instead of two:
`'standard'` (the face of the statement, as the SEC viewer shows it),
`'detailed'` (every dimensional row) and `'summary'` (non-dimensional totals
only). From 5.8.0 `include_dimensions` still worked and emitted a
`DeprecationWarning`. **6.0 removes it: passing it raises `TypeError`.**

```python
# Before
financials.income_statement(include_dimensions=True)
statement.to_dataframe(include_dimensions=False)
xbrl.statements.balance_sheet(include_dimensions=True).render()

# Now
financials.income_statement(view='detailed')
statement.to_dataframe(view='standard')
xbrl.statements.balance_sheet(view='detailed').render()
```

`include_dimensions=True` was translated to `view='detailed'` and
`include_dimensions=False` to `view='standard'`, so the rewrite returns exactly
what 5.x returned. Passing both `view` and `include_dimensions` already raised
`ValueError` in 5.x, so no working call combined them.

**Where it was removed:**

- `Financials.balance_sheet()`, `.income_statement()`, `.cash_flow_statement()`,
  `.statement_of_equity()` and `.comprehensive_income()`
- the same five methods on `xbrl.statements` (`Statements`)
- `Statement.render()` and `Statement.to_dataframe()`
- `Statements.to_dataframe(statement_type, ...)`, which now takes `view=`. In
  5.x it passed `include_dimensions` on to `render()` and so warned on every
  call; its default output (`'standard'`) is unchanged.

**Positional calls fail too.** On the five `Financials` methods
`include_dimensions` was the first parameter, so `financials.income_statement(True)`
meant `include_dimensions=True`. `view` is now keyword-only there, and so are
the parameters that followed `include_dimensions` in `Statement.to_dataframe()`
(`include_unit` onward) and `Statements.to_dataframe()` (`view`, `presentation`).
A 5.x positional call raises `TypeError` instead of handing its value to a
different parameter.

**Not affected.** `include_dimensions` stays on the APIs where it was never
deprecated and is not a spelling of `view`: `xbrl.current_period` statements
(`CurrentPeriodView.balance_sheet(include_dimensions=...)` and its siblings),
the multi-period `xbrls.statements` methods and `StitchedStatement`, and
`xbrl.query(include_dimensions=...)`.

**The mechanical rewrite** (check each hit is one of the methods listed above,
not a current-period or stitched statement):

```bash
grep -rn 'include_dimensions' .
sed -i '' -e "s/include_dimensions=True/view='detailed'/g" \
          -e "s/include_dimensions=False/view='standard'/g" your_script.py
```

## `edgar` now declares `__all__`

**What changed.** The top-level package declares its public API in `__all__`.
Until now there was no way to tell an API from an accident: everything reachable
from `edgar` looked equally official, including `Optional` and `partial`
(imported for annotations) and `Document`, which is the *legacy* `edgar.files`
parser and a different class from `edgar.documents.Document`.

**What breaks today: `from edgar import *` is narrower.** It no longer supplies
the names outside `__all__`. If you use star-import and something stops
resolving, import it from where it lives:

```python
# Before — arrived via `from edgar import *`
from edgar import *
doc = Document.parse(html)

# Now
from edgar.documents import Document
```

`edgar.Document` was the legacy parser, which 6.0 removed; see
[the `edgar.files` removal](#the-legacy-edgarfiles-parser-and-chunkeddocument-are-removed).

**Direct imports are unaffected.** `from edgar import <anything>` works exactly
as it did, listed or not.

**What is coming in 6.0.** Names outside `__all__` become private. They fall
into three groups: stdlib that leaked in through annotation imports; the three
names belonging to `edgar.files`, which are already gone; and internal plumbing that already
has a supported entry point in front of it — filesystem/config helpers, the
cache-clearing functions behind `clear_cache()`, and lower-level variants such
as `get_by_accession_number_enriched`.

**To check whether you are affected**, compare what you import against the list:

```python
import edgar
mine = {"Company", "Filing", "Document"}          # whatever your code imports
print(sorted(mine - set(edgar.__all__)))          # -> ['Document']
```

## `Filing.cik` and `Filing.company` on multi-filer filings

**What changed.** A filing with more than one filer now reports the *issuer*
where it used to report whichever filer the quarterly index happened to list
first, which was frequently the parent guarantor.

Resolving an accession — `find(accession)`, `get_by_accession_number(accession)`
— now goes through EDGAR full-text search, which orders a filing's filers
issuer-first. The quarterly index ordered them differently.

```python
from edgar import find

f = find("0001918704-25-005439")   # a BofA structured note

f.cik, f.company
# 5.x:  (70858,   'BANK OF AMERICA CORP /DE/')   <- the parent guarantor
# 6.0:  (1682472, 'BofA Finance LLC')            <- the issuer
```

**What did not change.** The set of filers is identical, and so is everything
you can reach from the filing:

```python
f.all_ciks       # [70858, 1682472] — same list, same order, both versions
f.all_entities   # still names both filers (the order differs)
f.text(), f.attachments, f.xbrl()   # identical; EDGAR serves the documents
                                    # under either CIK
```

**Rewrite rule.** If you read `.cik` or `.company` to identify *the* filer,
decide which filer you actually want and say so:

```python
# Before — implicitly "whichever filer the index put first"
issuer = filing.company

# After — say which one you mean
issuer = filing.company                       # the issuer, explicitly
every_filer = filing.all_entities             # all of them
if 70858 in filing.all_ciks:                  # membership, not identity
    ...
```

Single-filer filings — nearly all of them — are unaffected. Measured across 54
ground-truth accessions: 50 identical, 4 differing only in this way, none
failing to resolve.

**Scope.** Filings from before 2001 are outside the full-text index and still
resolve through the quarterly index unchanged, as does any lookup full-text
search cannot answer.

## `TableNode.to_dataframe()` row index

**What changed — shipped in 5.46.0.** A table whose first column header spans
several physical columns returns a plain row index instead of `None`-padded
tuples. If you are on 5.46.0 or later you already have this behavior and nothing
changes in 6.0. It is listed here for code written against an earlier 5.x.

Filings routinely lay the row-label column across two or three physical columns
that all carry the same header text, with only the first holding the label.
Before 5.46.0 *every* matching column moved into the index, so a label came back
as a tuple.

```python
table = document.tables[10]
df = table.to_dataframe()

list(df.index)[:1]
# before 5.46.0:  [('Gross written premiums by line of business:', None, None)]
# 5.46.0 on:      ['Gross written premiums by line of business:']

df.loc['Gross written premiums by line of business:']
# before 5.46.0:  KeyError
# 5.46.0 on:      works
```

Where the match came back two-dimensional, versions before 5.46.0 raised
`ValueError: Index data must be 1-dimensional` outright and you got no frame at
all.

**Rewrite rule.** Drop any tuple unpacking around index labels:

```python
# Before
for label, row in df.iterrows():
    name = label[0] if isinstance(label, tuple) else label

# After
for name, row in df.iterrows():
    ...
```

**Column count.** The empty columns left behind by the spanning header are
dropped, so most tables have the width they had before 5.46.0. A same-headed column
that holds real data — a percentage or a rate — is kept as data rather than
absorbed into the index, so a small number of tables are wider.

Measured across 1,940 tables in the benchmark corpus: 1,228 unchanged, 711 with
a scalar index in place of tuples, 31 wider, one that used to raise and now
converts, none returning less data. The corpus exposes the identical
1,026,693 non-blank cells before and after.

## `Document.to_dataframe()`

**What changed — shipped in 5.46.0.** It works. If you are on 5.46.0 or later
nothing changes in 6.0; this is listed for code written against an earlier 5.x.
Before 5.46.0 it raised on essentially every real annual or quarterly report,
from inside pandas or numpy, with one of:

```
ValueError: cannot join with no overlapping index names
TypeError:  Cannot cast array data from dtype('float64') to dtype('int64')
ValueError: Index data must be 1-dimensional
```

A filing's tables do not share a schema — one 10-K in the benchmark corpus has
71 tables whose column indexes are 1, 2, 3, 4, 10 and 17 levels deep — and
pandas cannot align those. Since 5.46.0 it flattens each table to single-level
string column names before stacking them.

```python
df = document.to_dataframe()

df.columns.nlevels          # always 1; every name is a str
df['_table_index']          # which table each row came from
df['_table_type']           # the table's classified type
df['_table_caption']        # its caption, or None
```

**Rewrite rule.** Remove any `try`/`except` you wrapped around this call, and
drop MultiIndex column handling — `df[('Revenue', '2024')]` becomes
`df['Revenue 2024']`. Header levels are joined with a space, with blanks dropped
and repeats collapsed, so `('Revenue', '')` and `('Revenue', 'Revenue')` both
become `'Revenue'`.

**When you want the real header structure**, use the per-table API, which still
preserves it:

```python
document.tables[i].to_dataframe()   # keeps MultiIndex columns
```

## `FactQuery.to_dataframe()` — the XBRL one

!!! warning "Two classes share this name"
    This applies to **`edgar.xbrl.facts.FactQuery`**, reached via
    `filing.xbrl().facts.query()`. It does **not** apply to
    `edgar.entity.query.FactQuery`, reached via `company.get_facts().query()`.
    Check which one you hold before changing code. Both classes change dtypes
    in 6.0, described in the next section.

**What changed — shipped in 5.46.0.** The column set follows the query's
*configuration* — the `include_*` flags and any names passed to
`to_dataframe()` — and no longer varies with which rows matched. If you are on
5.46.0 or later nothing changes in 6.0; this is listed for code written against
an earlier 5.x.

```python
q = filing.xbrl().facts.query()

q.limit(5).to_dataframe()
# before 5.46.0:  could return fewer columns than the same query unlimited,
#                 because columns that were null in those 5 rows were dropped
# 5.46.0 on:      same columns either way; unpopulated ones come back null

q.by_period_type('instant').to_dataframe()
# before 5.46.0:  period_start / period_end disappeared
# 5.46.0 on:      present and null

empty_result.to_dataframe()['decimals']
# before 5.46.0:  KeyError
# 5.46.0 on:      an empty column
```

**Rewrite rule.** Remove defensive column checks:

```python
# Before
if 'decimals' in df.columns:
    use(df['decimals'])

# After
use(df['decimals'])
```

Dtypes are unchanged for populated columns. A column with no data at all now
takes its declared dtype rather than whatever inference landed on.

## Fact DataFrames: integer and flag columns are nullable

**What changed — a quiet one.** Five columns that hold integers or flags, which
can be absent, now have pandas' nullable dtypes. An absent value is `pd.NA`
instead of `NaN`, and the dtype is the same for every query.

| Where | Column | 5.x | 6.0 |
|---|---|---|---|
| `filing.xbrl().facts.query().to_dataframe()` | `preferred_sign` | `float64` with `NaN`, or `int64`, depending on the query | `Int64` |
| | `fiscal_year` | `float64` or `int64`, depending on the query | `Int64` |
| | `is_dimensioned` | `bool`, or `boolean` on an empty result | `boolean` |
| `company.get_facts().query().to_dataframe()` and `EntityFacts.to_dataframe()` | `fiscal_year` | `int64`, or `float64` when no returned row had one | `Int64` |
| | `is_audited`, `is_estimated` | `bool`, or `boolean` when no returned row had one | `boolean` |

In 5.x the dtype depended on which rows matched. On Foot Locker's FY2024 10-K,
`query().to_dataframe()` read `preferred_sign` as `float64`, and
`query().by_statement_type('IncomeStatement').to_dataframe()` read it as
`int64`, because only the first matched a fact without a presentation sign.

```python
df = filing.xbrl().facts.query().to_dataframe()

df['preferred_sign'].dtype      # 5.x: float64 or int64    6.0: Int64
df['preferred_sign'].iloc[i]    # 5.x: nan for an absent    6.0: <NA>
```

**`numeric_value` and `value` do not change.** They stay `float64` with `NaN`,
so `np.isnan()` on them keeps working.

**Rewrite rule.** Test absence with `pd.isna()`, which matches `NaN` and
`pd.NA` alike, so the same code runs on 5.x and 6.0. The old tests do not raise
on `pd.NA`; they answer `<NA>` where they used to answer `True`, so a mask built
from them silently selects none of the absent rows:

```python
# Before — <NA> for an absent value, so df[missing] skips it
missing = np.isnan(df['preferred_sign'])
missing = df['fiscal_year'] != df['fiscal_year']

# After
missing = df['preferred_sign'].isna()
```

Two other patterns behave differently with `pd.NA`:

- **Truthiness raises.** `if row['is_audited']:` raises `TypeError` when the
  value is `pd.NA`. Use `row['is_audited'] is True`, or `fillna(False)` on the
  column first if absent should mean no.
- **`astype(int)` raises on `pd.NA`.** Drop or fill the nulls first, or keep the
  column as `Int64`.

## 10-K items on filings with a Cross Reference Index

**What changed.** `TenK.__getitem__` returned raw HTML on filings that route
through a Cross Reference Index — Citigroup, GE and Henry Schein among them —
while every other filing returned text. It now returns text everywhere.

```python
tenk = filing.obj()
tenk['Item 1']
# 5.x (Citigroup): 1,685,461 chars starting '<div style="min-height:36pt...'
# 6.0:               218,550 chars of text, opening on the Business overview
```

**Rewrite rule.** If you were parsing the returned markup, stop:

```python
# Before
from bs4 import BeautifulSoup
text = BeautifulSoup(tenk['Item 1'], 'html.parser').get_text()

# After
text = tenk['Item 1']
```

This affected filings unevenly — on Citigroup, `Item 1A`, `Item 7` and `Item 8`
already returned text while `Item 1` did not — so code that looked correct on
one item could break on another.

**Related.** An item whose Cross Reference Index row reads "Not Applicable", or
carries only an incorporation-by-reference marker, returns `None` rather than an
empty string. There is no such disclosure in the document, and an empty section
would present absence as content.

## Section keys and section content

**What changed.** Section extraction was substantially corrected in 6.0. No API
changed shape, but `document.sections` and `tenk.items` return different keys
and different content on filings that were previously mis-parsed.

If you have hardcoded section keys, lengths, or offsets, re-check them. The
changes that move the most:

- Filings that group items out of numeric order (Morgan Stanley) had sections
  that ran to the wrong end or vanished entirely; they are now bounded correctly
  and the missing ones are present.
- Filings using a Cross Reference Index (Citigroup) now expose canonical keys
  such as `part_ii_item_7`, where 5.x returned non-canonical keys like `mda` and
  gave nothing for the canonical name.
- Filings writing item headings as single-row tables (Wells Fargo) went from one
  section of wrong content to all 23 items.

**Rewrite rule.** Prefer canonical keys and check for absence:

```python
# Before — a key that only existed on some filings
mda = document.sections['mda'].text()

# After — the canonical key, absence handled
section = document.sections.get('part_ii_item_7')
mda = section.text() if section else None
```

## Underwriter extraction on registration statements

**What changed.** `RegistrationS1.underwriting` returned wrong rosters in two
directions, both now fixed. No API changed; the values did.

- A firm whose legal name contains "division of" — `EF Hutton, division of
  Benchmark Investments, LLC`, `ThinkEquity, a division of Fordham Financial
  Management, Inc.` — was rejected as parser junk, so `lead_manager` was `None`
  on every filing it led.
- A filing's *beneficial-ownership* table could be read as its underwriting
  syndicate, so `lead_manager` came back as the column header `'Before
  Offering'` and the roster listed individual directors.

**Rewrite rule.** Remove `None` fallbacks and name filters you added to work
around either:

```python
# Before
lead = uw.lead_manager or guess_from_cover(filing)
firms = [u.name for u in uw.underwriters if looks_like_a_firm(u.name)]

# After
lead = uw.lead_manager
firms = [u.name for u in uw.underwriters]
```

## Errors: one vocabulary, and `None` never means failure

There were 27 exception classes across ten packages with no shared base, of
which two were reachable from the top level — so `except` had to name a type
from whichever module happened to raise. There is now a root and four branches,
in `edgar.exceptions`:

```text
EdgarError
├── TransportError          we could not get an answer from SEC
├── NotFoundError           you named a thing and it does not exist
├── ParsingError            we got the bytes and could not build the object
└── ValidationError         your input was wrong before we ever asked
```

**Builtin catches keep working.** The branches inherit the builtin they
replace — `ValidationError` IS-A `ValueError`, `NotFoundError` IS-A
`LookupError` — so `except ValueError:` written against our raises keeps
catching them. Seven old class names were deprecated aliases for the same
objects in 5.x, and 6.0 removes them: importing one raises `ImportError`. The
new names work in 5.48.0 and later, so you can switch before upgrading. See
[Handling Errors](../guides/error-handling.md) for what to catch and why.

### Names removed in 6.0

| Old | New |
|---|---|
| `StatementNotFound` | `StatementNotFoundError` |
| `NoCompanyFactsFound` | `CompanyFactsNotFoundError` |
| `SECFilingNotFoundError` | `FilingNotFoundError` |
| `InvalidDateException` | `InvalidDateError` |
| `IdentityNotSetException` | `IdentityNotSetError` |
| `TooManyRequestsException` | `TooManyRequestsError` |
| `DataObjectException` | `DataObjectError` |

### What 6.0 changes

Each of these emitted a `FutureWarning` in 5.x naming what it would become,
and `EDGARTOOLS_STRICT_ERRORS=1` turned the 6.0 behaviour on early. In 6.0 it is
the only behaviour: the variable has no effect, and the helpers that staged the
change, `edgar.exceptions.strict_errors_enabled()` and `warn_will_raise()`, are
gone. If your code called `strict_errors_enabled()`, delete the call; the answer
is always yes.

| Call | 5.x | 6.0 |
|---|---|---|
| an HTTP failure escaping the network layer | propagates as `httpx2.ReadTimeout` and friends (`httpx.*` before 6.0, see [the HTTP client section](#the-http-client-moved-from-httpx-to-httpx2)) | raises `TransportError`, with the original as `__cause__` |
| `tenk["Item 99"]` — no such item | warns, returns `None` | raises `SectionNotFoundError` |
| `find("123456-99")` — malformed accession | warns, returns `None` | raises `ValidationError` |
| `filing.obj()` on a modelled form whose data will not read | warns, returns `None` | raises `DataObjectError` |
| `tenk.document` when the parser fails | warns, returns `None` | raises the parser's `ParsingError` |
| `get_financials()`, `get_quarterly_financials()`, `tenk.financials` on a filing with no XBRL | warns, returns a `Financials` whose accessors all answer `None` | returns `None`. The 5.x warning said this would raise `XBRLFilingWithNoXbrlData`; it does not (see below) |
| `search_filings("apple", start_date="2024-13-01")` — a query EFTS rejects | returns 0 results (EFTS answers with HTTP 200 and an error body) | raises `InvalidDateError` for a malformed date before any request, `TransportError` for any other rejected query. `next()` and `fetch_more()` stop at the 10,000-hit window EFTS will page through instead of requesting a page it refuses |

The `search_filings` row has no 5.x warning: a query EFTS rejects raises in
6.0.0 directly (GH #1497).

`filing.obj()` on a form edgartools does not model still returns `None`, and
so does `filing.xbrl()` on a filing without XBRL. `filing.html()` also keeps
returning `None` when the filing has no HTML primary document, which is
common: the primary document is a PDF, a text file or XML, or, since 5.59.0,
the index page lists no primary document at all, where it used to raise
`AttributeError`. Those are answers, not failures, and that distinction is
the point of the whole change.

The `get_financials()` row lands on the `None` side of that line, though in 5.x
it warned that it would raise. No XBRL is a property of the filing, exactly as
it is for `filing.xbrl()`: filings from before SEC's 2009-2011 XBRL phase-in have
none (`Company(104599)`, Circuit City, last 10-K filed 2008, is one), and a 6-K
or 8-K need not carry statements at all. What was broken in 5.x was the object
returned instead: it **passed** `if financials is not None:` and then yielded
`None` from `income_statement()`, `balance_sheet()` and `cash_flow_statement()`.
Returning `None` makes that guard correct. If you wrote
`except XBRLFilingWithNoXbrlData:` after the 5.x warning, replace it with the
`None` check; nothing raises that class.

Where the raising form is the only form, there is a non-raising one beside it:
`report.get(item, default)` is to `report[item]` what `dict.get` is to
`dict[...]`, and it never raises for a missing item.

## Settings and identity moved to `edgar.settings`

**What changed.** Connection settings and SEC identity now live in
`edgar.settings`: `EdgarSettings`, `set_identity`, `get_identity`,
`get_edgar_data_directory`, and the access modes (`NORMAL`, `CAUTION`, `CRAWL`).

The access modes moved, but they are also **deprecated and removed in 6.0** —
they never affected how edgartools talks to SEC. See
[Access modes are deprecated](#access-modes-are-deprecated) below.

They used to live in `edgar.core`, alongside quarter math, HTML sniffing, a pager,
thread helpers and the logger — only about a third of that 697-line module was
settings, and everything you are told to configure was in that third.

**Nothing breaks today.** `edgar.core` re-exports every one of those names, and
they are the *same objects*, so `is` comparisons and `isinstance` checks behave
identically:

```python
from edgar.core import get_identity      # works today, removed in 6.0
from edgar.settings import get_identity  # preferred
```

**Most code needs no change at all.** `set_identity` is re-exported on the
top-level namespace, which is how the documentation has always shown it:

```python
from edgar import set_identity          # unaffected, now and in 6.0
from edgar import CAUTION               # deprecated, warns today, gone in 6.0
```

**What 6.0 changes.** The `edgar.core` re-exports go. If you import any of these
from `edgar.core` directly, repoint at `edgar.settings` — or at `edgar`, for the
names it exposes. The access modes go entirely, from every path.

The rest of `edgar.core` — the logger, `listify`, the extension tables, HTML
sniffing, the pager and the thread helpers — stays where it is. The quarter
helpers have since moved too; see the next section.

## Access modes are deprecated

**What changed.** `EDGAR_ACCESS_MODE` and the `NORMAL` / `CAUTION` / `CRAWL`
objects are deprecated. Reading any of them, or setting the environment
variable, raises a `DeprecationWarning` in 5.x. They are removed in 6.0.
They are no longer in `__all__` of `edgar`, `edgar.core` or `edgar.settings`, so
`from edgar import *` no longer imports them or warns; `from edgar import CAUTION`
still works and still warns.

**Why.** The modes advertised a timeout, connection-limit and retry policy that
was never wired into the HTTP client. Nothing in the package read `edgar_mode`,
so all three modes behaved identically and selecting one never changed how
edgartools talks to SEC.

**What to use instead.** The two settings that do work:

```bash
export EDGAR_RATE_LIMIT_PER_SEC="5"   # replaces CAUTION / CRAWL: slow the request rate
export EDGAR_HTTP_TIMEOUT="25"        # per-request timeout in seconds
```

Both are documented in [Configuration](../configuration.md).

`EdgarSettings.limits` is removed in the same change. It ignored
`self.max_connections` and returned the module default, so every mode reported
`max_connections=10` regardless of what it declared. Nothing read it. The
module-level `limits` object is a different name and is unaffected.

## `FilingHomepage` takes an lxml tree, not BeautifulSoup

**What changed.** The filing index page is parsed with lxml instead of
BeautifulSoup since 5.53.0. Two call shapes that handed edgartools a soup
object kept working through 5.x with a `DeprecationWarning`. **6.0 removes both.**

| 5.x call (warned) | 6.0 |
|---|---|
| `FilingHomepage(url, soup=soup)` | `TypeError` (unexpected keyword `soup`); pass the tree as the second argument, `root` |
| a `BeautifulSoup` passed as `root` to `FilingHomepage(...)` or `Attachments.load(...)` | `TypeError: FilingHomepage takes an lxml tree, not BeautifulSoup ...` naming the replacement |

```python
# Before
soup = BeautifulSoup(html, "lxml")
homepage = FilingHomepage(url, soup=soup)

# Now
from edgar.attachments import parse_homepage_html
homepage = FilingHomepage(url, parse_homepage_html(html))
```

`parse_homepage_html` accepts `str` or `bytes`; prefer bytes, since lxml refuses
a `str` that opens with an encoding declaration, which SEC markup often does.

**You probably do not need to do anything.** `filing.homepage` and
`FilingHomepage.load(url)` build the tree themselves. This only affects code
that constructs a `FilingHomepage` or calls `Attachments.load` directly.

## `beautifulsoup4` is no longer a dependency

**What changed.** Every parser in edgartools runs on lxml, so 6.0 stops
installing `beautifulsoup4` (and its `soupsieve` dependency). Nothing in the
library imports it.

**What breaks.** Code of yours that does `from bs4 import ...` and relied on
edgartools to install bs4 gets `ModuleNotFoundError`. Add `beautifulsoup4` to
your own requirements.

**`edgar.xmltools` returns lxml elements only.** Its helpers accepted either a
BeautifulSoup `Tag` or an lxml element through 5.x; they now take lxml
elements. `find_element(xml_string, name)` and `find_all_elements(xml_string, name)`
still accept a raw XML string, but parse it with lxml and return
`lxml.etree._Element` objects rather than bs4 `Tag`s, so read results with the
module's own helpers instead of bs4 methods:

| bs4 on the result (5.x) | 6.0 |
|---|---|
| `el.text` | `element_text(el)` (whole subtree, as bs4 gave it; lxml's `el.text` stops at the first child) |
| `el.name` | `local_name(el)` |
| `el.find("x")` / `el.find_all("x")` | `find_element(el, "x")` / `find_all_elements(el, "x")` |
| `el.attrs["id"]` | `el.attrib["id"]` / `el.get("id")` |
| `if el:` | `if el is not None:` (a childless lxml element is falsy) |

To parse a whole document, call `edgar.xmltools.parse_xml(xml)`; it recovers
from malformed SEC XML the way bs4 did.

## The HTTP client moved from `httpx` to `httpx2`

**What changed.** edgartools now makes its requests with
[`httpx2`](https://github.com/pydantic/httpx2), the actively maintained fork of
`httpx`, instead of `httpx` itself. `httpx` has had no release since 0.28.1
(December 2024) and no longer takes bug reports; `httpx2` is maintained by
Pydantic and ships security fixes. It installs under its own import name, so the
two can sit side by side, and edgartools no longer depends on `httpx`.

How you call edgartools does not change. Four things can still reach your code.

**1. Exception types.** A network failure that escapes edgartools is now an
`httpx2` exception, not an `httpx` one. `httpx2` keeps the same class names and
hierarchy (`httpx2.ReadTimeout`, `httpx2.ConnectError`, `httpx2.HTTPStatusError`,
...), but they are different classes, so **`except httpx.ReadTimeout:` around an
edgartools call no longer catches anything**. It does not fail; it silently
stops firing, which is why this is the one to look for.

Catch `TransportError` instead. It is edgartools' own type, it does not depend
on which HTTP library is underneath, and in 6.0 the network boundary turns every
transport failure into one (see [Errors](#errors-one-vocabulary-and-none-never-means-failure)
above).

```python
# Before — never fires once edgartools runs on httpx2
import httpx
try:
    filings = company.get_filings(form="10-K")
except httpx.ReadTimeout:
    ...

# Now
from edgar.exceptions import TransportError
try:
    filings = company.get_filings(form="10-K")
except TransportError as e:
    if e.status_code is None:
        ...   # never got an answer: connection, DNS or timeout
```

If you cannot move to `TransportError` yet, `except (httpx.HTTPError, httpx2.HTTPError):`
is the bridge: it catches what edgartools raises today and what your own `httpx`
code raises.

The same applies to `httpx` objects you hand to edgartools. Functions that accept
a client, such as `edgar.httprequests.download_file_async(client, url)`, expect an
`httpx2.AsyncClient` now, and a request option such as `timeout=` must be a
number or an `httpx2.Timeout`; an `httpx.Timeout` raises `TypeError`.

**2. The logger name.** `httpx2` logs under `"httpx2"` and `"httpcore2"`, not
`"httpx"` and `"httpcore"`. edgartools quiets `"httpx2"` to `WARNING` the way it
quieted `"httpx"`. If you configured either logger yourself, rename it:

```python
# Before
logging.getLogger("httpx").setLevel(logging.DEBUG)

# Now
logging.getLogger("httpx2").setLevel(logging.DEBUG)
```

**3. Which certificates are trusted.** With verification on (the default),
`httpx2` checks SEC's certificate against your **operating system's** trust
store, through the `truststore` package edgartools already ships with. `httpx`
used the CA list bundled in the `certifi` package. On a typical desktop or
server this changes nothing you can see. Two cases notice it:

- Behind a corporate proxy that re-signs HTTPS traffic, the proxy's CA is
  usually installed in the OS, so requests that needed
  `configure_http(use_system_certs=True)` now succeed without it. That setting
  and `EDGAR_USE_SYSTEM_CERTS` still work and are now the same as the default.
- A minimal container image with no OS CA certificates (a slim image without the
  `ca-certificates` package, for example) now fails verification where `certifi`
  used to succeed. Install the OS CA package, or point `SSL_CERT_FILE` at a CA
  bundle, which `httpx2` honours.

`configure_http(verify_ssl=False)` and `EDGAR_VERIFY_SSL=false` still turn
verification off.

**4. `edgartools[ai]` installs still contain `httpx`.** The MCP SDK that the
`[ai]` extra installs depends on `httpx`, so it stays in those environments.
edgartools does not use it, and its presence changes nothing above.

Mechanical rewrite for the logger names:

```bash
sed -i '' -e 's/getLogger("httpx")/getLogger("httpx2")/' \
          -e 's/getLogger("httpcore")/getLogger("httpcore2")/' your_script.py
```

There is no mechanical rewrite for the `except` clauses, because the right
replacement is `TransportError` and that changes what the handler means.

## The legacy `edgar.files` parser and `ChunkedDocument` are removed

**What changed.** `edgar.files` was the HTML parser edgartools used before
`edgar.documents`. Everything in the library has run on `edgar.documents` for
several releases, and the old package shipped alongside it only so existing code
kept working. 6.0 deletes it, together with `ChunkedDocument` and the
`chunked_document` property on `TenK`, `TenQ`, `TwentyF`, `FortyF` and the 8-K
classes. Every route into it warned in 5.x: `chunked_document` from 5.49, the
`edgar.files` modules from 5.55, and `CurrentReport.doc` from 5.56.

**What breaks.** Importing anything under `edgar.files` raises
`ModuleNotFoundError`. `from edgar import Document`, `detect_page_breaks` and
`mark_page_breaks` raise `ImportError`; reading them as attributes
(`edgar.Document`) raises an `AttributeError` that says what to use instead.
`report.chunked_document` raises `AttributeError`.

| Removed | Use instead |
|---|---|
| `edgar.files.html.Document`, `SECHTMLParser`, `edgar.Document` | `filing.parse()`, or `edgar.documents.parse_html(html)`, which return `edgar.documents.Document` |
| `edgar.files.html_documents.HtmlDocument`, `get_clean_html` | `edgar.documents.parse_html(html)` |
| `edgar.files.htmltools.ChunkedDocument`, `report.chunked_document` | `report.items`, `report["Item 7"]`, `report.document.sections` |
| `ChunkedDocument.get_item_with_part(part, item)` | `TenK.get_item_with_part(part, item)` / `TenQ.get_item_with_part(part, item)` — markdown by default; pass `markdown=False` for plain text |
| `ChunkedDocument.tables()` | `report.document.tables` |
| `edgar.files.htmltools.html_sections` | `filing.sections()` |
| `edgar.files.htmltools.html_to_text`, `edgar.files.html_documents.html_to_text` | `filing.text()`, or `edgar.documents.parse_html(html).text()` |
| `edgar.files.markdown.to_markdown`, `html_documents.html_to_markdown` | `filing.markdown()`, `attachment.markdown()`, or `parse_html(html).to_markdown()` |
| `edgar.files.tables` (`TableProcessor`, `ProcessedTable`) | `document.tables`, and `TableNode.to_dataframe()` for a DataFrame |
| `edgar.files.styles` (`parse_style`, `get_heading_level`) | no public replacement; `document.headings` gives the headings the parser found |
| `edgar.files.text` (`XmlDocument`, `XMLHighlighter`) | no replacement |
| `edgar.files.page_breaks`, `detect_page_breaks()`, `mark_page_breaks()` | none — see [Page breaks](#page-breaks-are-not-rendered-any-more) below |

```python
# Before
from edgar.files.htmltools import ChunkedDocument
chunked = ChunkedDocument(filing.html())
business = chunked["Item 1"]
items = chunked.list_items()

# Now
tenk = filing.obj()
business = tenk["Item 1"]
items = tenk.items
```

**To find your call sites now**, while 5.x still warns rather than fails, run
your suite with `-W error::DeprecationWarning`, or search for the names:

```bash
grep -rnE "edgar\.files|ChunkedDocument|chunked_document|detect_page_breaks|mark_page_breaks|from edgar import .*\bDocument\b" .
```

## `CurrentReport.doc` returns the parsed document

**What changed.** On every other report class, `.doc` returns the parsed
`edgar.documents.Document`, the same object as `.document`. On `EightK` /
`CurrentReport` it returned the legacy `ChunkedDocument` instead, so one attribute
name meant two unrelated types depending on the form. It was deprecated in 5.56.
In 6.0, `.doc` on an 8-K is `.document`, as it is everywhere else, and it no
longer warns.

**What breaks.** Code that reads `ChunkedDocument` methods off an 8-K's `.doc` —
`.list_items()`, `.chunks_for_item()`, `.show_items()`, `["Item 2.02"]` and so
on — now gets an `AttributeError` or a different answer. Re-pointing it is not
enough; it needs the 8-K's own API:

```python
eightk = filing.obj()

# Before
eightk.doc.list_items()
eightk.doc["Item 2.02"]

# Now
eightk.items                 # ['Item 2.02', 'Item 9.01']
eightk["Item 2.02"]          # the item's text
eightk.doc.sections          # the parsed document, as on a 10-K
```

## Page breaks are not rendered any more

**What changed.** `Filing.markdown()`, `Attachment.markdown()` and
`Attachments.markdown()` no longer take `include_page_breaks` or
`start_page_number`, and `detect_page_breaks()` / `mark_page_breaks()` are gone.
All of them were deprecated in 5.x. Passing `include_page_breaks=True` was the
last thing that still routed a whole document through the legacy renderer,
which dropped every image.

**What breaks.** Passing either keyword raises `TypeError: ... got an unexpected
keyword argument 'include_page_breaks'`. Calls that never passed them are
unaffected.

**There is no replacement.** `edgar.documents` treats page-break rules and
page-number footers as print layout and drops them, so the information the
`{N}------` markers carried is not in the parsed document. If you used the
markers to split a filing into chunks, split on structure instead:

```python
# Before
md = filing.markdown(include_page_breaks=True, start_page_number=1)
pages = re.split(r"\{\d+\}-+", md)

# Now — passages cut at headings and tables
passages = filing.sections()
# or fixed-size chunks with overlap, for embedding
chunks = list(filing.parse().chunks(chunk_size=512, overlap=128))
```

## `Attachment.text()` and exhibit text read the same as `Filing.text()`

**What changed — a quiet one.** `Attachment.text()` on an HTML attachment, and
the exhibit text inside `EightK.text()` and `SixK.text()`, are now rendered by the
same rule as `Filing.text()`. Until 6.0, `Attachment.text()` and the 8-K exhibits
still went through the legacy parser and its fixed-width console layout; nothing
warned, because the call happened inside edgartools. `filing.grep()` reads
`Attachment.text()`, so its matches move with it.

**What you get back.** The same words, laid out the way `Filing.text()` lays them
out. Measured over 82 real filings from 2001 to 2026, the new text contains
every word the old text did, apart from two things it drops on purpose: running
page headers and page numbers, and the tail of any table cell longer than 500
characters, which is cut with `...` exactly as `Filing.text()` cuts it (about
0.02% of words). It also contains about 8% more words, because the old
layout broke long words across lines inside narrow table columns, so a search or
`grep` for those words found nothing.

`SixK.text()` was already on the new parser but cut table cells at 200
characters; it now uses the same 500 as everything else, which adds about 0.9%
more words and drops none. Exhibits that arrive as bytes in a Windows-1252
encoding keep their accented letters and curly quotes on all three paths.

**What to check.** Anything that parsed `Attachment.text()` by column position,
or matched the old box-drawn table borders, needs revisiting. Code that searches
the text for words or phrases needs nothing, and finds more than it did.

## `Filing.sections()` and `Filing.search()` passage boundaries

**What changed — a quiet one, and not a break.** `Filing.sections()`, which
`Filing.search()` indexes, splits the filing into passages with `edgar.documents`
rather than the legacy parser. This shipped in 5.56; it is listed here because it
is part of the same removal and because results you stored may not line up with
new ones.

**What you get back.** The same words in differently cut passages. The two
chunkers index the same words to within 0.10% across 41 era-stratified filings,
and mean recall@5 over 375 phrase queries is unchanged at 99.2%. Passage counts,
passage lengths and therefore `search()` scores and result order differ, so code
that stored passage indexes or compared scores across versions should recompute
them.

## Standard concepts: corrected mappings

**What changed — a quiet one.** About 450 entries in the XBRL standardization
mappings named the wrong standard concept. They are corrected: some are
retargeted to the concept the element actually measures, and the rest, where no
standard concept fits, now have none. Most of the wrong ones put a detail line
under its section total (a cash-flow line marked as "Net Cash from Operating
Activities"), or under a concept that measures something else (cash taxes paid
as income tax expense).

This changes the `standard_concept` column of `Statement.to_dataframe()` and
`render(standard=True)`, the answers of `ReverseIndex.lookup()` and
`get_standard_concept()`, and anything you computed by grouping on
`standard_concept`. Labels are untouched: the filer's own wording is kept, as
before.

Apple's FY2023 cash flow statement (`0000320193-23-000106`):

```python
cf = filing.xbrl().statements.cash_flow_statement()
df = cf.render(standard=True).to_dataframe()
# concept                                      5.x                               6.0
# us-gaap_PaymentsOfDividends                  DistributionsToMinorityInterests  CommonDividendsPaid
# us-gaap_PaymentsForProceedsFromOther...      NetCashFromInvestingActivities    None
# us-gaap_ProceedsFromPaymentsForOther...      NetCashFromFinancingActivities    None
# us-gaap_IncomeTaxesPaidNet                   IncomeTaxes                       None
# us-gaap_InterestPaidNet                      InterestExpense                   None
# us-gaap_ShareBasedCompensation               StockBasedCompensationExpense     StockBasedCompensationCF
```

5.x, because the "Other" line was counted as the total; the filed figure is
$3,705M. Other measured examples:

### `EntityFacts.get_concept()` synonym groups

Eighteen synonym-group members, and three tags under legacy labels, measured a
part, a larger total or a different measure than their concept, and are removed.
Snowflake's `get_concept("operating_lease_liability")` returned a 10-Q's $37.1M
current portion in 5.x; it now returns the $413.7M total.

A company that reports only the current and noncurrent parts of a liability,
with no total, gets `None` for that concept where 5.x returned one of the parts.
For operating leases that is roughly one lease reporter in eight (625 of 4,807
filers at 31 December 2023, from SEC's frames data). If you need a figure for
those filers, add the parts yourself:

```python
current = facts.get_concept("OperatingLeaseLiabilityCurrent")
noncurrent = facts.get_concept("OperatingLeaseLiabilityNoncurrent")
```

### Industry no longer changes standard concepts

`filing.xbrl().standardization.industry` was always `None` in 5.x. It is now set
from the filing header's SIC code, so JPMorgan's FY2025 10-K reads `Banks`. The
per-industry overrides it would have applied are removed, because each one only
restated, narrowed or swapped the base mapping, so the industry no longer
changes any standard concept. Setting `industry` by hand changed concepts in
5.x; it no longer does.

### Parenthetical statements a filing does not have

`balance_sheet(parenthetical=True)`, `income_statement(...)`,
`cash_flow_statement(...)` and `statement_of_equity(...)` returned the primary
statement in 5.x when the filing had no parenthetical statement of that kind.
They now return `None`. Most filings have no income-statement or cash-flow
parenthetical: Apple's FY2023 10-K returns `None` for both, and a balance sheet
parenthetical only.

```python
# Before — silently the primary statement when there was no parenthetical
cf_paren = xbrl.statements.cash_flow_statement(parenthetical=True)
df = cf_paren.to_dataframe()

# After
cf_paren = xbrl.statements.cash_flow_statement(parenthetical=True)
if cf_paren is not None:
    df = cf_paren.to_dataframe()
```

Selecting a statement by its role URI also changed: it returns that role's own
rows and periods, where 5.x could return another statement's.

## Still to come

Planned for the 6.0 breaking window and **not yet shipped**. Do not write code
against these; each will get a section above when it lands.

| Change | What to expect |
|---|---|
| Public API **enforcement** | `__all__` is already declared (see below) — 6.0 makes the names outside it private, and some currently-importable names will move. |
| Source tree reorganisation | Module locations change; import paths follow. The first moves have landed and have their own section above — `edgar.effect` and `edgar.form144`. Further moves will each get a section as they ship. |
| Schedule 13D/G figures a filing does not report | `ReportingPerson`'s six ownership figures, `total_voting_power`, `total_dispositive_power`, `Schedule13D`/`Schedule13G` `total_shares` and `total_percent`, and `OwnershipComparison.shares_change`, `percent_change` and the share and percent values of `get_summary()` become `None` where the filing does not report the figure, instead of reading it as `0`. 5.x already has the `None`-returning form: `ReportingPerson.reported(figure)`, `ReportingPerson.unreported_fields`, and `OwnershipComparison.reported_shares_change` / `reported_percent_change`; `shares_change` and `percent_change` emit a `FutureWarning` when they read an unreported figure as `0`. A reported `0` stays `0`. |
